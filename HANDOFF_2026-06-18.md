## Assumptions & Important Context

### Architecture Assumptions
1. **Gold mirrors = production SP output** — `main.regtech.gold_regreportdb_prod_dbo_*` tables are exact mirrors of SSMS tables updated daily by the data platform team
2. **Nightly cleanup drops staging table metadata** — all `main.regtech_ops_stg.bi_output_regtechops_*` tables use external LOCATION to survive this. Delta files persist; metadata re-registers on next run.
3. **NB04 REMOVED (2026-06-19)** — Regulation movements staging notebook eliminated entirely. All consumers read gold directly:
   - NB07 regchange cells → `main.regtech.gold_regreportdb_prod_dbo_reg_migrationinout_population`
   - NB06 audit tables → `main.regtech.gold_regreportdb_prod_dbo_reg_regulation_movments_positions`
   - Orchestrator Step 4 is now a no-op (documentation-only comment)
   - NB04 notebook retained in repo for historical reference only

### Logic Assumptions
1. **ext_position dedup**: SP uses `ROW_NUMBER() OVER (PARTITION BY PositionID, OpenORClose ORDER BY CloseOccurred DESC NULLS LAST) = 1`. Our ext_position doesn't have an OpenORClose column — it's a raw position table. A single deduped row with both OpenOccurred+CloseOccurred generates BOTH O and C events in NB08. So `PARTITION BY PositionID` alone (without OpenORClose) is correct for our architecture.
2. **NPD TRAX self vs gold**: Self-referencing only works when (a) running daily without gaps AND (b) full PII detection is active. In masked mode or with date gaps, gold is the only correct baseline.
3. **Customer scope filter**: The +109/+91 CID excess is consistent across dates and doesn't grow proportionally — suggesting a static eligibility filter (like FTD) rather than a dynamic condition.
4. **RegulationID filtering**: MIFID2_Report uses RegID IN (1,2,9) for EU/UK scope and RegID=11 for ME. IsMifid=1 on instruments. IsMifidByFCA=1 for UK (448 FCA-only instruments with IsMifid=0).

### What Could Still Be Wrong (beyond documented gaps)
1. **Partial close edge cases**: NB08 Cell 6 removes ~42K children 'O' events from partial closes. If the SP handles partial close differently (e.g., different dedup logic or aggregation), some edge cases may differ.
2. **ChangeLog timing**: NB05 reads `mifid2_ext_positionchangelog` with a date window. If the bronze source has late-arriving records, our window might miss some vs the SP which reads real-time.
3. **Instrument SCD snapshot timing**: We use `gold_regreportdb_prod_dbo_reg_instruments_scd` which is a daily snapshot. If IsMifid changes for an instrument mid-day, our snapshot might differ from SP's real-time read.
4. **Mirror table filtering**: NB05 reads ext_mirror with date window. If mirror entries arrive late or have different timestamp precision, we could miss some.
5. ~~**Hedge execution HBC**~~: RESOLVED — the -160 was caused by stale Fivetran LP data, not HBC logic.

## Production Operations Guide (for Data Engineering)

### Scheduling
- **report_date**: Should be set to `yesterday` (T-1). The widget default is hardcoded for testing; in production, pass `date_sub(current_date(), 1)` from the Lakeflow Job parameter.
- **use_masked_fallback**: Set to `false` once `main.pii_data` access is granted. Until then, keep `true`.
- **npd_history_source**: Set to `self` once running daily without gaps AND `use_masked_fallback=false`. Until then, keep `gold`.
- **Recommended schedule**: Daily at **07:00 UTC** (after upstream bronze refreshes complete, typically by 06:00 UTC).

### Expected Runtime
- Full orchestrator (12 steps): **~25-35 minutes** on serverless compute
- Heaviest steps: Step 5 (ext_staging, ~12 min), Step 6 (customer, ~15 min), Step 8 (report output, ~8 min)
- Steps 1-4: ~5 min combined. Steps 9-12: ~10 min combined.

### Idempotency
- **All steps are fully idempotent** — every table uses `CREATE OR REPLACE TABLE ... USING DELTA LOCATION`
- Safe to re-run from Step 1 at any time without cleanup
- Safe to re-run individual steps (respecting dependency order: Steps 1-5 before 6, Step 6-7 before 8, etc.)
- The `LOCATION` pattern ensures Delta files persist through nightly UC metadata cleanup

### Compute Requirements
- Runs on **serverless** (current validated configuration)
- Requires access to: `main.regtech_ops_stg` (write), `main.regtech` (read), `main.general` (read), `main.trading` (read), `main.bi_db` (read)
- **BLOCKER**: `main.sharepoint` — needs `USE_SCHEMA` grant (see Fix #7 in this doc)
- **BLOCKER**: `main.pii_data` — needs access grant for unmasked PII (production mode)

### Upstream Data Dependencies
- Bronze tables refresh overnight (ETL completes by ~06:00 UTC)
- Key sources: `bronze_etoro_trade_positionforexternaluse`, `bronze_etoro_history_position_datafactory`, `bronze_etoro_history_hedgeexecutionlog`
- If bronze is delayed, the orchestrator will still run but may produce stale results for that day
- Gold mirrors (`main.regtech.gold_regreportdb_prod_dbo_*`) refresh independently — used for audit/comparison only

### Failure Handling
- If a step fails: check the child notebook's output for the specific error
- Most common failure: nightly cleanup dropped table metadata → re-run from Step 1 (re-registers all tables)
- NB03 temp INSERT: if Fivetran source changes row count, the INSERT may cause duplicate LiquidityAccountIDs. Switch to SharePoint source (Fix #7) to eliminate this risk.
